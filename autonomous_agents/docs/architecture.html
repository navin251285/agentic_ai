Overview

One Python process owns all state and runs the simulation. The browser only displays a snapshot that the server pushes every 0.5 seconds. The backend is FastAPI on uvicorn with exactly one worker, because state lives in memory. It persists to CSV files through a repository interface and calls Gemini 2.5 Flash-Lite on Vertex AI, under a hard budget of 10 calls per minute. The frontend is React 18 with TypeScript, a Zustand store fed by Server-Sent Events, Recharts and Tailwind, served by Vite.

All business rules (product states, badges, countdowns, the scoreboard) are computed in the backend. React only formats, groups and animates.

The simulation tick

One asyncio task ticks every 0.5 real seconds. Simulated time (sim_s) advances by 0.5 × speed per tick, so all durations are in sim seconds and freeze when paused. Each tick runs, in order:

  1. Clock. Advance sim_s; drop curveballs that have ended.
  2. Shop. Serve every customer due: a basket of 1–4 distinct items, weighted by popularity and any curveball multiplier. Customers arrive every 2–4 sim s, or every 1–2 in rush hour or a crowd curveball. Returns the baskets it drew.
  3. Supplier. Move open orders through confirmed (10%), shipped (30%) and delivered (100% of the time to delivery). A delivery is capped at the shelf's maximum.
  4. Agent. Apply any finished Gemini answer, then run a check if one is due (every 5 sim s by default).
  5. Shadow shop. Serve the same baskets, deliver, and run its rules check at the same moment.
  6. Publish. Hand the snapshot to the SSE hub. It is serialised once per tick, and only when someone is listening.

Every API action (sell, edit, settings, curveball, reset) takes the same lock, so actions and ticks never interleave. Services take an injected random generator and are driven by tick(dt), so tests replay exact runs without sleeping.

Agent decision flow

Zones and when Gemini is asked

  • Must-order zone: no open order and stock at or below the reorder mark. Watch zone: no open order and stock up to 1.5 × the mark.
  • A product becomes pending when it newly enters either zone. At a check, one call covers every pending product. A "wait" answer stands until the product changes zone.
  • A curveball, or switching to Gemini while one is active, makes the next call cover every product without an open order.
  • The call runs in the background, with at most one in flight. Its answer is applied on a later tick against the state at that moment, so the simulation never waits for the AI.

Call budget

LlmRateLimiter keeps a rolling window of real-time call timestamps (time.monotonic, so speed changes can't exceed the budget). It allows a call only with fewer than 10 calls in the last 60 s and at least 6 s since the previous one. It is checked before a request is built, and every call counts, including the warm-up and failed calls. Configuration can lower the limits but never raise them.

The call itself

LangChain's ChatGoogleGenerativeAI with with_structured_output against a Pydantic schema, temperature 0, no retries. The compact JSON context holds:

  • For each product asked about: its zone, stock, maximum, mark, room, both lead times and sales in the last 60 sim s.
  • Shop-wide: open orders with their supplier, rush hour, supplier delay and any active news.

The answer is a one-line situation plus, for each product, order (with quantity and supplier) or wait, with a reason of at most 20 words. Timeout (8 s), errors and invalid output trigger a rules fallback, an AGENT_FALLBACK event and a warning log. Each call is logged with its count for the current minute.

Guardrails (every engine, rules included)

Drop unknown products and products that already have an open order; clamp quantity to 1 … room; and if a must-order product was skipped or answered "wait", the rules order it (source "fallback"). An engine may order earlier or smaller, but can never leave a shelf to run empty.

Curveball and shadow shop

CurveballEffect on the world (both shops)What the agent is told
HeatwaveCrowd (rush-hour arrivals) + cold drinks × 3, for 180 sim sThe news text and the seconds left; never the mechanics
Cricket finalCrowd + chips, cold drinks, biscuits × 2.5, for 180 sim s
Supplier strikeMain-supplier orders placed during it are due at strike end + lead time
Typed textNone (agent only)
  • Suppliers: main = lead time (× 1.5 with supplier delay), no fee. Backup = 40% of the lead time (at least 5 sim s), ₹2 per unit, never delayed. The rules always use main.
  • Brain switch: a curveball switches a Rules brain to Gemini, because the rules can't read news.
  • Shadow shop: it receives the same baskets (drawn once by the real shop), manual sales, edits, settings and curveball effects, and checks at the same moments. It writes no events. Its stock, orders and counters persist in runtime.json. With the Rules brain both shops stay identical; a test checks this every tick for 600 sim s on every scenario.
  • Scoreboard: missed sales × ₹15 + backup fees, for each shop; agent_ahead_by = rules total − agent total.
  • Calibration: one press at 1x makes the rules shop miss at least 10 sales, and a scripted news-aware agent beats it on every seed (median +₹142 heatwave, +₹228 cricket, +₹333 strike). Overusing the backup can lose. A test guards this.

scenarios/*.csvRead onlynormal_day, rush_hour, low_stock_start
  • Encoding: files are UTF-8 with a BOM, so they open correctly in Excel.
  • Failed writes: a write that fails (for example, a file locked open in Excel) logs a warning and is retried. Events that fail to append are queued and written in order on the next success.
  • Broken products.csv: it is renamed to products.csv.bad-<timestamp> and the default scenario loads.
  • Startup: always paused; the last speed is restored, so Play resumes it.
  • Runs: each reset or scenario load starts a new run_id and restarts sim time at 0. History is filtered by run.

Storage sits behind InventoryRepository (load, save products/orders/runtime, append/read events, scenarios). A Postgres implementation can replace the CSV one without touching services, API or UI.

Frontend

  • useLiveState opens an EventSource on the stream and writes each snapshot to a Zustand store. If the connection drops, it reconnects and shows a banner.
  • Actions call typed fetch wrappers and apply the returned snapshot at once, before the next tick arrives.
  • The chart fetches /api/history when the selected product gets a new event or a new run starts. It draws the agent's line, the rules shop's dashed line, the reorder mark, the danger zone and order/delivery markers.
  • VITE_BASE serves the whole UI under a path prefix, for JupyterLab's proxy; API and SSE calls follow it. In development, Vite proxies /api to VITE_API_TARGET, so no CORS is needed.
  • Animations are CSS transitions of at most 600 ms, and they respect reduced-motion settings.

Testing

  • Backend: 217 pytest tests, with ruff for linting. They cover rules, the CSV repository (atomic writes, bad files, queued events), the simulation, agent batching, the limiter (10 virtual minutes at 5x, never more than 10 calls in any 60 s), guardrails, the API, SSE, curveballs and shadow-shop equality.
  • Calibration tests: the seed stock keeps a normal day at ≤ 3 missed sales over 600 sim s, and one curveball press gives a sensible agent a real win.
  • No real AI calls in tests: they use fake LLMs. One opt-in pytest -m live makes a single real call; never run it while the demo is running.
  • Frontend: 63 Vitest + React Testing Library tests, plus a strict TypeScript check, ESLint and a production build.
  • Headless runs: python -m app.run_sim --fast replays runs without real-time waiting and never writes the live files.

Design decisions

DecisionWhyTrade-off
In-memory state, one workerSimple, fast, one lock prevents racesNo horizontal scaling; restart reloads from files
Full snapshot over SSE every tickThe UI is a pure view; reconnecting is trivialMore bytes than deltas (small at 10 products)
Sim time separate from real timePause and speed-up work everywhere; tests need no sleepsThe AI budget must use real time, handled separately
Gemini in the background, event-drivenThe shop never waits; few calls (about 3–5 a minute at 1x)Decisions can land one tick later
Rules as guardrail and fallbackThe demo never breaks; shelves never run dryThe AI can order earlier or less, but never skip a low shelf
One structured call, no tool-calling loopPredictable cost and latencyThe agent picks from a fixed menu of actions
Shadow shop for comparisonSame customers make the gap attributable to decisionsDuplicated state; typed news cannot change the world
CSV behind a repositoryVisible and editable on disk for the demoNot for real volumes; swap in Postgres via the interface
