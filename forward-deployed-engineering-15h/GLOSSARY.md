# Glossary
- **access token** — the short-lived string a client sends on each call to prove what it may do; here a signed JWT (lesson 13)
- **allow-list** — a list of the only items something may use: tools an agent may run (lesson 19), or host names an egress proxy forwards to, with every other host refused (lesson 15); the check is in code, never the prompt alone
- **ambiguity** — a request with no test of success yet; the first job is to turn it into one question that data can answer (lesson 30)
- **assumption** — something you believe without proof yet; it goes on a list and gets tested (lesson 02)
- **audit log** — an append-only record of who did what to which record, and when; it holds ids and times, never the content it audits (lesson 27)
- **backoff** — waiting longer after each failed try (for example 0.2 s, then 0.4 s, then 0.8 s), so a struggling server gets room to recover (lesson 04)
- **base unit** — the one unit every quantity is converted to before totals are added, such as each (not dozens) or grams (not kilograms) (lesson 05)
- **baseline** — the value of a measure today, before the work starts; the yardstick for a target (lesson 03)
- **batch job** — a run over many records (orders, rows) that nobody waits on live; it must finish by a deadline and survive a restart (lesson 24a)
- **bearer token** — a secret string sent in the `Authorization: Bearer <token>` header to prove who is calling; treat it like a password (lesson 04)
- **billable work** — work the customer has agreed in writing to pay for; extra asks outside the plan are unpaid until a change request is signed (lesson 08)
- **blameless postmortem** — a written review of an incident that asks what happened and what to change, not who to blame (lesson 17)
- **business case** — a short written comparison of cost and value over a stated period, with every input labelled as measured, agreed or a guess (lesson 30)
- **cache hit** — a request answered from saved earlier output, with no model call; a miss calls the model and saves the answer (lesson 18)
- **capstone** — the lesson that puts the parts of a course together on one real delivery, from scope to handover (lesson 31)
- **change request** — a written request to add or change work after the plan is agreed, with its effect on days and cost (lesson 08)
- **characterisation check** — a check that runs the old and the new code on the same input and confirms they agree wherever the old code was right; every other difference needs a reason in the log (lesson 25)
- **check (validation)** — plain code that runs after a model's output and compares it with the source before any action; a form that passes the types is not yet proof that its facts are true (lesson 06)
- **circuit breaker** — a switch in the client that stops calls to a failing route after too many failures, answers at once with the fallback, and lets one test call through after a cooldown (lesson 28)
- **client credentials** — the OAuth 2.0 grant in which a service account trades its client ID and client secret for a token, with no person logging in (lesson 13)
- **client secret** — the password of a service account; it lives in a secret store or `.env`, never in code or a notebook output (lesson 13)
- **codify (a pattern)** — turn a fix that repeats across customers into a shared component, template or playbook the product team owns (lesson 01)
- **Cohen's kappa** — agreement between two graders after removing the agreement they would reach by chance alone; 1 is perfect, 0 is chance, below 0 is worse than chance (lesson 12)
- **config** — the settings that hold one customer's rules (stable key, date formats, unit table), passed into shared code so the code itself does not change (lesson 25)
- **Container** — a running copy of an image, isolated from the host and from other containers (lesson 14)
- **Container image** — a sealed, versioned build of an app with its packages and Python version, made from a Dockerfile (lesson 14)
- **core** — the shared part of field code that serves many customers unchanged, with each customer's rules passed in as config (lesson 25)
- **cost per resolved case** — the monthly bill divided by the queries a person did not have to check; the number a customer can compare with the work done (lesson 29)
- **cursor pagination** — reading a long list in pages, where each reply holds an opaque `next_cursor` for the next page and a null cursor marks the last one (lesson 04)
- **custom** — code that encodes one customer's own decision or rule; it stays in that customer's folder or behind one function (lesson 25)
- **cut line** — the point in a ranked list where the sprint's time runs out; items above it are in, items below go to the backlog (lesson 03)
- **data residency** — the rule that customer data is stored and processed only in the regions the contract names (lesson 27)
- **decomposition** — splitting a vague request into smaller problems, each with an observable, a test and an owner (lesson 02)
- **deduplication** — keeping one row per stable key, so a copy in the export is not counted twice (lesson 05)
- **delivery drill** — a timed run of the whole delivery path for a new customer, from scope to handover, that finds the gaps before go-live (lesson 32)
- **demo script** — a written plan for a live demo: the order of the steps, what each step should show, and what it must not claim (lesson 07)
- **discovery** — asking about the failure before the fix: what went wrong, how often, for whom, and what people did next (lesson 02)
- **discovery interview** — a conversation built for discovery, with open questions and follow-ups on facts and numbers (lesson 02)
- **Docker Compose** — a tool that starts several containers from one YAML file, on a private network, with their settings and health checks (lesson 14)
- **Dockerfile** — the recipe that builds an image, step by step: base image, packages, code, user, start command (lesson 14)
- **egress proxy** — the one controlled path from a private network to outside hosts; it allows or refuses each host and logs every call (lesson 15)
- **ETL** — extract, transform, load: read the source, fix and reshape it, then write it where the next step reads it (lesson 05)
- **eval (evaluation)** — a repeatable test for an AI feature: fixed inputs, the expected answer for each, a scorer and a score that can be compared between versions (lesson 10)
- **eval harness** — a repeatable script that runs a system's outputs against a fixed test set and scores them (lesson 25)
- **eval set (golden set)** — the labelled cases an eval runs on, with the expected answers written before the feature runs (lesson 10)
- **evidence pack** — the answers to a security questionnaire, each with a pointer to a file, setting, log or test that a reviewer can rerun, plus a list of gaps (lesson 27)
- **expand, deploy, contract** — the three-step order for a data change: add the new column with a safe default (expand), deploy code that reads it, and remove the old column only in a later release (contract) (lesson 24)
- **expectation reset** — a written update that moves a date or scope, with the reason, a new date you can meet, and what the customer must confirm (lesson 30)
- **failure drill** — a planned, controlled break of a dependency, run before a customer finds it, to see what users get and how the system recovers (lesson 28)
- **fallback** — a simpler answer used when the main path fails, such as keyword rules instead of a model; it is labelled, so nobody mistakes it for the normal answer (lesson 28)
- **field report** — a short, evidence-backed note from the field to the product team: the repeated request, how often it came back, what it costs, the rows or runs that prove it, and one decision to make (lesson 26)
- **fixed cost** — a cost that does not change with volume, such as hosting, monitoring or eval runs (lesson 29)
- **forward deployed engineer (FDE)** — a software engineer who works inside the customer's environment, owns the outcome to go-live and sends repeatable patterns back to the product (lesson 01)
- **gap (security review)** — a questionnaire item with no evidence yet; it is written down with an owner and a date, never answered with a yes (lesson 27)
- **gate** — the rule that stops a release when an eval shows a regression (lesson 10)
- **glue code** — the code that connects two systems, such as a script that reshapes a customer's export for our product (lesson 01)
- **go-live** — the day the customer's real work runs on the service, not a test or demo environment (lesson 01)
- **graceful degradation** — a service keeps answering, with less capability, while a dependency is down (lesson 28)
- **grader** — what marks an answer right or wrong: code, a model or a person (lesson 10)
- **gross margin** — the contract price minus the cost of delivering it, as a share of the price (lesson 29)
- **guardrail** — a check, in code, that stops an unsafe action at run time (lesson 10)
- **half-open** — the breaker state after the cooldown, when one test call decides whether the breaker closes or opens again (lesson 28)
- **handover** — the transfer of a deployed service to the customer's team, with docs and training, so it runs without the engineer who built it; the point where the customer's team takes over, backed by a handover pack (docs, runbook, on-call path) and a rehearsal (lessons 01, 21, 22)
- **handover page** — the one-page summary the handover writes for the customer's team: what runs, where it is documented, who owns each part (lessons 20, 31)
- **Health check** — a command the runtime runs on a schedule to say whether a container is healthy; `depends_on` with `service_healthy` waits for it (lesson 14)
- **health gate** — the rule that a rollout moves to the next node only if the new node passes its health check; a failed check stops the rollout (lesson 24)
- **holding answer** — a reply to a question you cannot answer yet: what you know, who finds out and by which day; it never guesses (lesson 07)
- **idempotency key** — a unique string a client sends with a write; the server saves the first answer under it and returns that answer for any repeat, so a retry cannot write twice (lesson 04)
- **Image tag** — the version label of an image (for example `bb-triage:1.0.0`); pin a full tag, never `latest`, so a rollback has a target (lesson 14)
- **impact** — how much harm a risk does if it happens, on a 1 to 5 scale (lesson 08)
- **in-flight calls** — calls that are sent but not yet answered; the concurrency a node runs at once (lesson 24a)
- **incident** — an unplanned break in a service a customer relies on; you mitigate first, then find the cause (lesson 17)
- **ingestion** — getting a customer's data into your system from its files or feeds, checked before it is trusted (lesson 05)
- **inter-rater agreement** — how often two graders give the same verdict; percent agreement is the raw share, kappa corrects it for chance (lesson 12)
- **internal network (Compose)** — a Compose network with no route to the outside; its containers reach each other and nothing else (lesson 15)
- **Jaeger** — an open-source trace store and web UI that shows the spans of one request as a timeline (lesson 16)
- **jitter** — a random extra wait added to each backoff, so many clients do not retry at the same moment (lesson 04)
- **JWT (JSON Web Token)** — a token made of a readable payload (claims such as `sub`, `scope`, `exp`) and a signature; the payload is not secret, the signature proves who issued it (lesson 13)
- **kill criterion** — a rule agreed before the work starts that stops a POC early, such as a data file not arriving by day 3 (lesson 03)
- **latency budget** — the longest wait you allow for one call or one case, measured on real calls (lesson 18)
- **least privilege** — giving each caller only the permissions it needs, and no more (lesson 13)
- **likelihood** — how probable a risk is, on a 1 to 5 scale (lesson 08)
- **Little's law** — in a steady system, the number in flight equals the arrival rate times the time each one takes; it sizes the calls in flight for a deadline (lesson 24a)
- **live demo** — a run of the work in front of the reader, rehearsed from a script, with its limits said aloud (lesson 07)
- **LRU cache** — a cache that drops the least recently used entry when full; `functools.lru_cache` is the standard-library version (lesson 18)
- **manifest (run manifest)** — the saved plan of a run: the input's checksum, the row count and the expected count per part (lesson 24a)
- **MCP (Model Context Protocol)** — an open protocol in which one MCP server exposes tools with schemas and any MCP client calls them the same way (lesson 19)
- **MCP client** — the program that starts or connects to an MCP server, lists its tools and calls them; an agent or a chat app is a client (lesson 19)
- **MCP server** — a process that exposes tools (and resources, prompts) over MCP; here `apps/19/basket_tools_server.py` (lesson 19)
- **metric (histogram)** — a number counted over many requests, such as how many took under 0.5 s; Prometheus stores it and graphs it (lesson 16)
- **milestone** — a point in time with no work of its own, such as a go/no-go check or a decision (lesson 08)
- **mitigation** — an action that lowers a risk's harm. In the risk register (lesson 08) it is done before the risk happens; in a runbook (lesson 17) it is the step that stops the harm during an incident, often a rollback (lessons 08, 17)
- **mock API** — a small stand-in for an outside service, built to run offline; here it is invented data and stands in for a customer's order system (lesson 04)
- **model grader (LLM judge)** — a model that marks another model's output pass or fail against a written rubric; its verdicts must be measured against a person (lesson 12)
- **multi-tenancy** — one running product serving many customers or stores, with each one's data kept apart (lesson 01)
- **NO_PROXY** — the host names a client calls directly instead of through the proxy, such as internal service names (lesson 15)
- **non-goal** — something the POC or project will not do, written down with a reason and a place the work goes (lesson 03)
- **normalise** — trim spaces and fix case so that equal things compare equal, for example `' bb-1003 '` and `'BB-1003'` (lesson 05)
- **observable** — the number or record that would change if the problem were fixed, such as missing-item tickets per week (lesson 02)
- **OIDC (OpenID Connect)** — a login layer on top of OAuth 2.0 that tells an app who the person is; used for single sign-on with a customer's identity provider (lesson 13)
- **on-call** — the person who is paged and must act when an alert fires, outside working hours (lesson 17)
- **OpenTelemetry (OTel)** — the vendor-neutral standard and SDKs for traces, metrics and logs; the Collector receives its data and forwards it (lesson 16)
- **OpenTelemetry Collector** — a service that receives telemetry from apps, batches it and sends it on to a trace store, so apps do not need to know the backend (lesson 16)
- **OTLP** — OpenTelemetry Protocol, the wire format spans and metrics travel in from an app to a Collector (lesson 16)
- **ownership matrix** — a table that names one owner for each part of a deployed system after handover; the vendor team must not appear as owner (lesson 22)
- **partition (part)** — one slice of a batch, chosen by a stable hash of its key, so every node knows its share (lesson 24a)
- **payback period** — the months until the yearly gain from a project covers its one-off build cost (lesson 30)
- **PII (personal data)** — information that identifies a person, such as an email address, a phone number or a card number; redacted before storage where the contract requires (lesson 27)
- **pipeline** — a fixed sequence of small steps that turns raw input into clean output, with counts printed at each step (lesson 05)
- **pool tenancy** — one shared deployment serving every tenant, with each tenant's data kept apart by a key, schema or file (lesson 23)
- **presales** — the work before a contract: discovery, a demo and a small proof of concept that shows the approach fits (lesson 30)
- **product backlog** — the ordered list of work the product team has agreed to build (lesson 01)
- **Prometheus** — an open-source metrics store: it scrapes numbers from apps on a timer and answers queries about them (lesson 16)
- **proof of concept** — a small, working test on real data that answers one question before a full build (lesson 01)
- **provider route** — the customer's only path to a model provider (a gateway or proxy); a drill can break it without touching the provider (lesson 28)
- **rate limit** — a cap on how many calls a client may make in a time window; going over returns 429 Too Many Requests (lesson 04)
- **reconciliation** — comparing the output's counts with the plan or the source, part by part, before a run counts as finished (lesson 24a)
- **red-team candidate** — a deliberately wrong prompt that the gate must refuse, to show that the gate can say no (lesson 32)
- **refactor** — change a program's structure without changing what it does on purpose; any other change in results is a bug to explain (lesson 25)
- **reference architecture** — the standard set of parts a solution needs and how they connect (data source, connector, model or agent service, evals and guardrails, API or UI, customer VPC deployment, runbook); reused for each customer (lesson 21)
- **regression** — a case that passed before a change and fails after it (lesson 10)
- **regression eval** — the set of cases that must keep passing; a change that fails one is blocked (lesson 10)
- **regression test** — a pytest check that fails when a case that passed in the shipped version fails in the candidate; the gate blocks the release on it (lesson 11)
- **release cycle** — the schedule of planned product releases; a fix for one customer waits for the next one (lesson 01)
- **Release diff** — the exact code change between two versions, shown to a change board before a deploy (lesson 14)
- **release gate** — a rule that stops a release unless the evidence passes: here a pass rate on the eval set and no regression on any case the shipped prompt passes (lesson 20)
- **release note** — the file the gate writes (tag, prompt, verdict, numbers, cost); the deploy reads it first and stops if the gate did not pass (lessons 20, 31)
- **replay** — running the same work again under the same run id; with upserts it writes nothing new (lesson 24a)
- **restore drill** — a scheduled test that restores a backup to a scratch file, checks it and times it, before it is needed (lesson 17)
- **retention** — how long a record is kept before it is deleted, as set in the deployment and the contract (lesson 27)
- **retry** — sending a failed call again; safe only for failures that a later try can fix, and for writes that carry an idempotency key (lesson 04)
- **retry budget** — a cap on retries, shared by all requests, so retries cannot multiply an outage; lesson 28 names it and builds only per-call caps (lesson 28)
- **Retry-After** — a response header that tells the client how many seconds to wait before it tries again (lesson 04)
- **reusable component** — core code used by two or more customers, with its own tests and an owner who decides changes (lesson 25)
- **reviewed-label export** — a file of delivery messages with the label an agent chose; the ground truth a triage is scored against (lesson 03)
- **risk** — something that might happen and hurt the plan (lesson 08)
- **risk register** — the table that lists every risk with its score, owner, mitigation and trigger (lesson 08)
- **Rollback** — starting the previous, known-good image again after a bad release, without a new build (lesson 14)
- **rolling upgrade** — replacing the copies of a service one at a time behind a proxy, so the rest keep answering during the change (lesson 24)
- **RPO (recovery point objective)** — how much data, counted back in time from the last backup, you may lose (lesson 17)
- **RTO (recovery time objective)** — how long a service may be down before it is back (lesson 17)
- **rubric** — the short written rules a grader applies to decide pass or fail; the shorter and more specific, the more consistent the grader (lesson 12)
- **runbook** — a written procedure for one known incident: symptom, first check, mitigation (the step that stops the harm, often a rollback), verify, escalation (lesson 17)
- **SAML SSO** — single sign-on in which the customer's identity provider signs an XML assertion that says who the person is; set up with the customer's IT team (lesson 13)
- **schema** — the defined shape of a record: its field names, types and allowed values, such as a Pydantic class (lesson 06)
- **scope** — a named permission inside a token, such as `orders:read` or `credits:write`; the API checks it on every call (lesson 13)
- **score (risk)** — likelihood times impact; used to sort risks so the riskiest is read first (lesson 08)
- **scrape** — Prometheus fetching an app's `/metrics` page on a fixed interval (lesson 16)
- **series** — one counted line in a metric store: one metric name with one unique set of label values (lesson 16)
- **service account** — an identity for software (not a person) with its own client ID, secret and scopes (lesson 13)
- **silo tenancy** — one deployment per customer: strong separation, many copies to upgrade (lesson 23)
- **SOC 2** — an audit report that an independent auditor issues on a company's security controls over a period (Type II); a team cannot award it to itself (lesson 27)
- **source (of a number)** — the request log, or a run someone can repeat, that a field report names next to each number; a number with no source is a guess and the report check refuses it (lesson 26)
- **span** — one timed step inside a trace, such as a call to the customer API, with a name, a start and a duration (lesson 16)
- **sponsor** — the customer-side person who backs the project and can unblock access and decisions (lesson 01)
- **sprint** — a fixed period of work, here two weeks or 10 working days (lesson 03)
- **stable key** — the columns that name one real thing the same way in every export, such as an order number, or the whole cleaned line when the export has no id; the basis for deduplication (lesson 05)
- **stakeholder** — anyone with a stake in the outcome: a user, a buyer, or a person who must sign off (lesson 02)
- **STAR** — behavioural-interview story format: Situation, Task, Action, Result (lesson 07)
- **status update** — a one-page note for a non-engineer: where we are, what we know, the decision needed with an owner and a day, and the risks (lesson 07)
- **stdio transport** — the client starts the server as a subprocess and talks to it over its standard input and output (lesson 19)
- **step limit** — the most model calls an agent loop may make before it stops, so a loop cannot run forever (lesson 19)
- **structured log** — a log line written as JSON fields (event, order id, duration, trace id), so a tool can filter it instead of a person reading text (lesson 16)
- **structured output** — a model's answer in a fixed shape, such as JSON that matches a schema, instead of free text; checked when it arrives (lesson 06)
- **success criterion** — a number a POC must reach, with an observable, a baseline, a target, a test and an owner (lesson 03)
- **success metric** — a number the customer can check, with a baseline, a target, a test, an owner and the customer's signature (lesson 08)
- **support tier** — a level of help (tier 1 desk, tier 2 owning team, tier 3 vendor team by agreement) with the team and hours that answer it (lesson 22)
- **technical win** — the point when the customer's technical people agree the approach works (lesson 30)
- **tenant** — one customer whose data must stay apart from the others; in this course one Basket Bazaar store (lesson 23)
- **thin slice** — one workflow carried all the way through, end to end, so every step is tested together before the rest is built (lesson 09)
- **time box** — a fixed end date for work; the date stays and the scope is cut to fit (lesson 03)
- **time to live (TTL)** — how long a cached entry may be used before it expires and is fetched again (lesson 18)
- **timeline** — an ordered list of tasks with a start day and an end day (lesson 08)
- **token** — the unit a model reads and bills, about three-quarters of an English word (lesson 18)
- **token budget** — the most input tokens you allow for one call; output is kept small with `max_output_tokens` (lesson 18)
- **tool calling** — the model asks the program to run a named function with arguments it chooses; the program runs it and returns the result, so the model never touches the system itself (lesson 06)
- **trace** — the list of spans for one request, linked by one trace id, across every service it touched (lesson 16)
- **trace id** — the id that links a log line, a span and a trace to the same request (lesson 16)
- **training drill** — a staged fault that the customer on-call team fixes alone, with the FDE team off the keyboard, scored against written steps and a time limit (lesson 22)
- **triage** — sorting an incoming message into a label, here missing item, late, damaged or wrong item, and from lesson 06 also other (lessons 03, 06)
- **trigger** — the observable sign that a risk is happening, so the team acts early (lesson 08)
- **unit economics** — the cost and revenue of one unit of work, such as one query, one resolved case or one customer for one month (lesson 29)
- **unplaceable** — a row whose date matches none of the known formats: it is counted, kept with an empty date, and stops the run only when the count is over the agreed limit (lesson 05)
- **upsert** — a write that inserts a row, or updates the row that already has the same key (lesson 24a)
- **value-based selling** — justifying the work by the outcome the customer gets, not by hours or features built (lesson 30)
- **variable cost** — a cost that grows with volume, such as model tokens or staff time for checks (lesson 29)
